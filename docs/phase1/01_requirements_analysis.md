## 0. 本書の位置づけと読み方

### 0.1 目的
P2P（Purchase-to-Pay）導入を検討している企業に対し、**購買業務の現状（As-Is）と課題を分析し、Phase1でシステム化すべき範囲を「業務要求」として確定する**。本書は「何を作るか（機能）」を決める前段として、「誰が・何に困っていて・何を実現したいのか（Why）」を明らかにする。

### 0.2 基本スタンス
- **機能一覧（F01-xx 等）を結論として使わない。** 機能一覧は「解の候補」であり、要求ではない。本書は現場のペインから要求を積み上げ、その結果としてどの機能を採用するかを次工程（要件定義）で逆算する。
- **将来要件は先取りしない。** Phase2 以降で扱う内容は範囲に含めない。必要になった時点で影響調査して設計変更する。そのために「なぜ Phase1 では扱わないか」を本書に明記する。

### 0.3 前提の扱い（重要）
本件は導入検討段階であり、実在の顧客ヒアリングに相当する情報は存在しない。そのため本書では**分析者が実務上妥当な前提を置き、それを「前提（A-xx）」として第9章に一覧化する**。前提は確定事項ではなく、実プロジェクトではヒアリングで検証すべき仮説である。前提として明示することで、後日「実態と違った」場合に見直し箇所を特定できる状態を担保する。

## 1. 対象企業（分析対象）

### 1.1 会社概要

| 項目 | 内容 |
|---|---|
| 社名 | 株式会社ミナミ技研（仮） |
| 業種 | 産業機器の受託設計・小規模製造（BtoB） |
| 従業員 | 42名 |
| 拠点 | 本社一拠点のみ |
| 組織 | 正式な部署区分はまだない。役割で緩やかに分かれている段階 |
| 取引通貨 | 日本円のみ（海外取引なし） |
| 会計 | 既存の会計ソフト（クラウド会計）を経理が別途使用中 |

### 1.2 導入検討に至った背景（なぜ今か）
- 直近1年で人員が32名 → 42名に増え、**購買の発生件数と関与者が増加**した。
- ある月に、**受領前・内容未確認のまま請求書を支払ってしまう事故**が発生（後で数量違いが判明し取引先と再調整）。社長が「購買のプロセスが見えていない」ことに危機感を持ったのが直接のトリガー。
- 「誰が何をいくらで買ったか」を後から追えず、社長・経理ともに月次の実態把握に手間取っている。

> この背景により、導入の第一目的は**「業務効率化」よりも先に「購買プロセスの可視化と統制（証跡・突合）」**にある。この優先順位は要求の優先度付け（第6章）に反映する。

## 3. 現状業務（As-Is）

### 3.1 代表的な業務シナリオ

**シナリオA｜現場社員が消耗品を買いたい（少額・都度）**
1. 設計の田中が「試験用治具が壊れた、買い直したい（約3万円）」と考える
2. Slackで上長の佐藤に「これ買っていいですか」とURLを貼る
3. 佐藤が「OK」とスタンプ → **承認の記録は Slack に流れて消える**
4. 田中が総務の鈴木にDMで発注依頼
5. 鈴木が取引先へ電話/メールで発注 → **発注記録は鈴木のメールにしかない**
6. 数日後に納品。**受け取った人がバラバラで、受領の記録なし**
7. 月末に取引先から請求書（郵送/PDF）→ 経理へ

**シナリオB｜総務が定期消耗品を発注（トナー・用紙）**
- 鈴木の裁量でルーチン発注。承認プロセスは事実上ない。

**シナリオC｜高額機材の購入（約50万円）**
- 現場 → 上長 →「これは社長に相談」→ 口頭/メールで社長判断 → 総務が発注。**社長判断の記録は残らない。**

**シナリオD｜請求書と発注が合わない**
- 届いた請求書の金額/数量が想定と違う。経理が総務に「これ何の発注？」と問い合わせ。総務が過去メールを掘り返す。**一次情報の所在が誰にもない。**

### 3.2 業務ボリューム（前提に基づく推定）
非機能要求の根拠にするための定量把握。数値は前提（A-08）。

| 指標 | 推定値 | 備考 |
|---|---|---|
| 月間の購買依頼件数 | 約 80〜120 件 | 42名規模・製造業の一般的水準として仮置き |
| 1件あたり平均明細数 | 1〜5 明細 | 消耗品〜機材まで |
| 取引先数 | 約 50〜80 社 | 継続取引が中心 |
| 同時利用者数（ピーク） | 5〜10 名程度 | 全社員がログインするが常時操作はしない |
| 高額（社長承認相当）の割合 | 全体の 1割未満 | 大半は少額の都度購買 |

> この規模感から、Phase1 は**高トラフィック・高並行性を前提とする必要はない**。非機能要求（第7章）はこの前提に立つ。

## 5. 業務要求（Business Requirements）

ペインを解消するために「業務として実現したいこと」。**How（画面・操作・担当割り）ではなく What/Why のレベル**で記述する。各要求は解消するペインにトレースする。

| ID | 業務要求 | 解消するペイン |
|---|---|---|
| R1 | 購買の依頼から請求承認までを、1つのつながった流れとしてシステム上に記録したい | P1, P3 |
| R2 | 誰がいつ承認・却下したか、誰が発注・受領・請求を登録したかを証跡として残したい | P1, P2 |
| R3 | 購入の妥当性を承認で統制したい。特に**高額な購買は社長が承認**できるようにしたい。承認の基準（金額の閾値）は運用側で見直せるようにしたい | P2 |
| R4 | 発注・受領・請求の三者を突き合わせ、数量・金額のズレを検知し、ズレたまま支払いへ進まないよう止めたい（三点照合） | P4, P5 |
| R5 | 同じ請求書を二重に登録・処理してしまうことを防ぎたい | P6 |
| R6 | 承認済みで突合の取れた請求だけを経理へ渡し、経理は既存の会計ソフトで支払処理を継続したい | P5, P6 |
| R7 | 各人が「自分が今対応すべきこと（承認待ち・発注待ち・受領待ち・差異対応）」を一目で把握したい | P1 |
| R8 | 過去・進行中の購買文書を、種別ごとに検索して探し出せるようにしたい | P1, P3 |
| R9 | 退職・担当変更が起きても、進行中の購買が止まらないよう、担当を引き継げるようにしたい | P8 |

> **R3 の決定事項:** 「高額は社長」の実現方式は、要件定義以降で詰める設計詳細（税抜/税込判定、対象文書範囲、社長自身の申請時の扱い、承認待ち中に閾値をまたいだ場合の再判定等）を除き、要求レベルでは「**金額閾値で承認者が上長→社長に切り替わる一段承認／閾値は設定で変更可能**」で確定。二段承認・部署条件・多段承認は Phase1 では扱わない（Phase9 送り）。詳細な検討経緯は付録Aに記録。

## 6. 要求の優先度と受入基準

### 6.1 優先度（MoSCoW）
導入の第一目的が「可視化と統制」であること（1.2）を反映する。

| 優先度 | 要求 | 理由 |
|---|---|---|
| Must（必須） | R1, R2, R3, R4, R5, R6 | 導入トリガー（統制・突合・二重払い防止）に直結。これが無ければ導入意義がない |
| Should（推奨） | R7, R8 | 日常運用の効率と定着に強く効く。Phase1 で提供する価値が高い |
| Could（任意） | R9 | あると安心だが、40名規模では発生頻度が低い。緊急再割当で最低限は担保 |
| Won't（今回やらない） | 第8章のスコープ外を参照 | Phase1 では扱わない |

### 6.2 Phase1 の成功基準（導入して「成功」と言える状態）
- 購買の 8割以上が Slack/口頭ではなくシステム経由で起票される（定着）
- 承認・受領・請求の突合が取れていない請求は、経理へ渡らない（統制）
- 経理から総務への「これ何の発注？」という問い合わせが実質ゼロになる（可視化）
- 高額購買はすべて社長の承認記録が残る（責任の所在）

## 8. スコープ（対象範囲の明確化）

### 8.1 Phase1 の対象範囲（In Scope）
- 認証・利用者管理・ロール・取引先管理・自社情報
- 購買申請 → 発注 → 受領 → 請求 の一連の起票・承認・照合
- 三点照合（全量取引・完全一致ベース）と差異の保持
- 承認済み請求書を経理へ「渡す」ところまで（渡した後はシステム外）
- 文書種別ごとの検索、利用者の基本検索、要対応ダッシュボード
- 承認・操作・変更の履歴

### 8.2 スコープ外（Out of Scope）と、その理由・送り先

| 対象外の領域 | Phase1 で扱わない理由 | 送り先 |
|---|---|---|
| 支払実行・仕訳・未払残管理 | 経理の既存会計ソフトで継続。購買側の責務ではない | 業務外 |
| 会計システム連携・外部支払結果 | まず手渡し運用で回す。連携は効果検証後 | Phase5 |
| 部署・組織階層・部署別承認 | 現時点で正式な部署が存在しない | Phase9 |
| 予定不在の代理・担当引継ぎ（通常運用） | 40名規模では頻度低。緊急再割当で最低限担保 | Phase10 |
| 分納・分割請求・残数量管理 | まず全量取引で運用を固める | Phase11 |
| 複数発注の統合請求 | 同上 | Phase12 |
| カタログ・品目マスタ・一括取込 | まず自由入力で運用を固める | Phase7, 13 |
| レポート・分析・購買集計 | 可視化はダッシュボードで最低限。分析は効果検証後 | Phase5, 18 |
| 予算管理・社員経費 | そもそも本システムの業務範囲外 | 業務外 |
| 下書き・複製・添付プレビュー等の入力補助 | まず基本フローを通す | Phase2 |
| 二段/多段承認・全員承認・金額以外の分岐条件 | Phase1 は「金額による承認者切替（一段）」まで | Phase9, 16 |

## 付録A. 論点1（承認方式）の検討経緯

要求 R3 の確定に至る検討過程の記録。将来「社長承認・金額分岐をどう決めたか」を追えるように残す。

- **当初案 (a):** 金額分岐はシステムに載せず、高額は運用（Slackで社長OK）でカバー。
  → **撤回。** 「証跡を残したい」という導入動機に対し、最も証跡が欲しい高額案件をシステム外へ逃がすのは本末転倒のため。
- **代替案の比較:**
  - (あ) 閾値超で承認者が上長→社長に**切り替わる**（一段のまま）
  - (い) 閾値超で上長+社長の**二段**
  - (う) 一段のまま、高額は社長に**通知のみ**
