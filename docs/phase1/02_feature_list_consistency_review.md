# Phase1 機能一覧整合レビュー（利用者・ロール／業務ルール／画面・帳票）

**作成日：2026-09-09**
**基準：05 実装機能一覧の採用42機能を「正」とする**
**照合対象：02 利用者・ロール・AS-IS／TO-BE、03 業務ルール、06 画面・帳票一覧**

> 採用42機能を正としたとき、他3文書に過不足がないかを照合した結果。
> 指摘はすべて「機能ID・画面数(21)・帳票数(1)を変えず、説明・ロール欄の補記で解決できる範囲」に収めている。

## 0. 結論

機能・画面・帳票の**対応そのものはほぼ整合**している。42機能すべてに主画面または共通適用場所(COM)が対応し、孤立画面もない。
一方、機能一覧を正としたとき、他3文書側で**説明・ロール欄が機能の含意より薄い箇所**が4点ある。うち#2・#3は、要件定義でアクセス制御(F01-12)を具体化する前提になるため、Phase1要件定義へ進む前に方針だけ確認することを推奨する。

## 2.【重要度：高】L05（経理）による発注・受領照会の権限が画面/ロールで弱い

### どこが問題か
- 05 の F01-26（発注照会）・F01-27（受領進捗）・F01-38（受領照会）の主な利用者は「発注／受領の閲覧権限者」。
- 03 P1-BR-INV-06 は、経理が「実際の注文、全量受領…を確認する」と規定。→ **経理(L05)は請求確認のため発注内容・受領内容を照会する必要がある**。
- しかし 02 §1.2 の L05 閲覧範囲は「対象購買の根拠を照会し」にとどまり、06 の SCR-016（発注詳細）・SCR-021（受領詳細）の利用者ロール欄に **L05 が明示されていない**（請求側 SCR-024／026 には L05 明記あり）。

### 何が起き、誰が困るか
- 経理が請求登録・確認時に、根拠となる発注・受領の詳細を開けるか、画面のロール欄だけでは読み取れない。
- 要件定義でアクセス制御(F01-12)を具体化する際、経理の閲覧範囲が発注・受領詳細に及ぶかが曖昧なまま渡る。

### どう修正するか（仮案）
- 06 SCR-016・SCR-021 の利用者ロールに **L05（請求根拠の照会のため）** を追記。
- または COM-01／F01-12 の説明に「経理は請求登録・確認の根拠として、対応する発注・受領の詳細を照会できる」を1行追加。
- 02 §1.2 の L05 行にも「対応する発注・受領の内容照会を含む」と補う。

### 何を確認すれば判断できるか
- 経理に発注・受領の**内容全体**まで見せるか、請求登録に必要な範囲（明細・数量・確認結果）に限るか。
- ここは権限設計の論点として要件定義へ渡す前提。まず「照会できる入口がある」ことだけ明記すれば足りる。

## 3.【重要度：中】L01/L04 一般社員の「請求登録有無」表示先の画面が不明確

### どこが問題か
- 02 §1.2・03 P1-BR-CMN-05 は「L01・L04だけの人は自分の申請に対応する発注・受領と**請求登録の有無**まで」と規定。
- F01-28（発注の請求登録進捗照会）・F01-55（関連文書照会）がこの「有無」を提供する。
- しかし 06 の SCR-016（発注詳細）ロールは「発注の閲覧権限者」、SCR-024／026（請求一覧・詳細）は「L03・L05・L07の許可範囲」で **L01 が除外**。→ **一般社員が「請求登録の有無」だけをどの画面で見るのか**が画面一覧から追いにくい。

### 何が起き、誰が困るか
- 依頼者が「自分の案件、請求まで登録されたか」を確認したいとき、請求一覧(SCR-024)は権限外、発注詳細(SCR-016)で有無だけ見えるのか、関連文書照会(COM-02)経由なのかが不明。
- 要件定義でアクセス制御を組む際に迷う。

### どう修正するか（仮案）
- 06 §3.2 または COM-02 に「L01・L04 は、自分の申請に連なる発注・受領・請求の**登録有無と関連番号**を関連文書照会で確認できる。請求の金額・明細など内容全体は開けない」と明記。
- SCR-011（申請詳細）概要に「関連する発注・受領・請求の登録有無を表示」を1行追加し、入口を明確化。

### 何を確認すれば判断できるか
- 「有無」を見せる入口を申請詳細(SCR-011)に置くか、発注詳細経由にするか。
- 業務上は依頼者が自分の申請から辿るのが自然なため、**SCR-011 起点を推奨**。

## 4.【重要度：中】利用者・取引先の画面集約方針が未記述

### どこが問題か
- 06 §6 の対応表に F03-08 → SCR-034 の行はあり整合。
- しかし F03-06／07／02／04／09 が独立一覧画面(SCR-019／024／010／014／035)を持つのに対し、**利用者検索(F03-08)だけが管理画面(SCR-034)に同居**。設計判断として妥当だが、06 §2 に「利用者一覧」相当の見出しがなく、他検索との**粒度が不揃い**に見える。

### 何が起き、誰が困るか
- 後続の要件定義者が「なぜ利用者検索だけ独立画面がないか」を判断できず、SCR-034 に検索・一覧・詳細・招待・停止・ロール付与が集約された理由を追いにくい。実害は小さいが説明不足。

### どう修正するか（仮案）
- 06 §1 の粒度説明に「利用者関連（照会・検索・管理・招待・停止・ロール）は SCR-034 に集約する。取引先も同様に SCR-035 へ集約する」と**集約方針を1行明記**。件数(21画面)は変えない。

### 何を確認すれば判断できるか
- 他の文書検索が業務区分ごとに一覧画面を分ける中で、利用者・取引先だけ集約する方針を意図どおりとするか。

## 5.【重要度：低】F01-16／F03-09 の SCR-012 での役割分担が二重定義気味

### どこが問題か
- 06 §6 で F01-16 → SCR-035／SCR-012／COM-01、F03-09 → SCR-035／SCR-012 と、両機能が申請登録画面(SCR-012)に対応。
- 05 で F01-16 は「照会」、F03-09 は「検索・絞り込み」。SCR-012 で申請者が取引先を「探して選ぶ」のは検索(F03-09)＋候補情報表示(F01-16)の合わせ技だが、**どちらが候補一覧を出し、どちらが選択後の情報表示か**が文章化されていない。

### 何が起き、誰が困るか
- 実害は小さいが、SCR-012 上での担当機能が曖昧。要件定義で画面項目を割り付ける際に判断が要る。

### どう修正するか（仮案）
- 06 SCR-012 概要「利用中の取引先を名称・識別情報等で探して選び」に **（F03-09で検索、F01-16で候補の識別情報を確認）** と括弧書きで対応機能を添える。実装粒度には踏み込まない。

## 6. 過不足なしを確認した部分（評価できる点）

- **42機能すべてに主画面 or 共通適用場所(COM)が対応**。06 §6 対応表で漏れた機能IDなし。
- **孤立画面なし**。21画面すべてが42機能のいずれかに紐づく。
- **帳票 RPT-001(発注書PDF) → F01-33** の1対1対応が整合。RPT-002／003 を作らない判断も05・06で一致。
- **除外14画面が不採用機能・運用移管と矛盾しない**：
  - SCR-031(承認設定)除外 ↔ 承認外部化
  - SCR-032(単位マスタ)除外 ↔ 単位直接入力
  - SCR-013(申請編集)除外 ↔ 申請直接編集なし
  - いずれも02・03・05・06で一貫。
- **L02 欠番**の扱いが 02・03・05・06・TODO で一貫。
- F01-20（申請の発注進捗）と F01-28（発注の請求登録進捗）、F04-05（受領の非数量訂正）等も03・06で整合。

## 7. 要件定義へ引き継ぐ論点

- #2・#3 の権限範囲（経理・一般社員に「内容全体」まで見せるか、「有無／根拠」に限るか）は**アクセス制御(F01-12)の具体化論点**。
- 本レビューの修正は「照会できる入口があること」だけ明記し、**範囲の確定は要件定義へ引き継ぐ**。
- 修正は説明・ロール欄の補記のみ。採用42機能・21画面・1帳票の件数は変更しない。
